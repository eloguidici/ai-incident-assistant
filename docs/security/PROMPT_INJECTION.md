The assessment section 1.2 asks for an explanation of unsafe input and prompt injection; it does not mandate a scanner, library, second model, or agents. The application adds a small native TypeScript `RegExp` observer to its existing data/instruction separation, input limits, no-tools policy, output validation and human review. It is not a security verdict or a blocking guardrail.

`detectPromptInjectionSignals` in [the detector](../../apps/api/src/ai/prompt-injection-signals.ts) scans a normalized copy (Unicode compatibility, accents, selected zero-width characters, whitespace, case) of the content selected for the provider. The observer does not modify that content; PII sanitation is a separate earlier step when enabled. Six closed identifiers cover instruction overrides, role spoofing, prompt disclosure, secret exfiltration, fabricated evidence and forged delimiters. The observer adds no external service, extra model call, dependency, schema field or confidence score. Reading an analysis adds `assistantInstructionsNoted`, computed from the stored incident text. The Incident tab shows that note when it is true. The note is not a verdict, and the analysis still runs. Detector changes require review, versioning and regression; its version is independent of the prompts.

## Use cases and data flow

1. Create: authenticate, validate and sanitize the source before reserving content/execution rows when PII is enabled. Retry: enforce ownership and policy eligibility, then reuse the protected stored source. Observe the selected incident before model invocation; manual retry observes again, not every gateway retry. Input-sanitation failure stops content writes/provider calls; output-sanitation failure occurs after a clean-input call and discards the raw response.
2. Follow-up: enforce ownership, policy eligibility, quotas and context budget; sanitize the new question before its writes, then observe protected incident, selected history and question before invocation. Both prior user and assistant content are untrusted data. Failed exchanges, dropped messages and text beyond the 1,000-character history limit are not scanned because they are not sent. Truncation can end earlier to avoid cutting a valid PII token.
3. Incident describing an attack: a quoted malicious instruction can emit a signal and still be analyzed. It is not rejected, erased or given a different prompt.
4. Signal plus bad output: schema, foreign URLs or other checks may reject output; nonexact quotes are omitted rather than automatically rejecting the whole response. Observation cannot bypass checks. A failed question preserves the prior valid analysis.
5. No signal: continue normally; this does not establish that the input is safe. Encoded or semantic attacks can evade the patterns.
6. Invalid input or unauthorized request: existing checks reject before observation/model invocation. A logging transport failure cannot turn observation into blocking.

Logs emit at most six events per input block (18 across a question's three blocks), deduplicated per rule/block. `prompt_injection_signal` contains `analysisId`, server-generated UUID `correlationId`, `securityDetector`, `securityRule` and `securityInput`, not matched excerpts, hashes, offsets or a copy of the input. Client correlation headers are not trusted as log identifiers. HTTP logs use route templates or `unmatched`; the supplied nginx raw request logs are disabled. The three security fields are restricted to closed values by the [log redactor](../../apps/api/src/common/log.ts). See the [data policy](DATA_POLICY.md) and [runbook](../operations/RUNBOOK.md); these scoped settings do not certify every dependency/collector, immutable audit or automatic alerts.

## Reproducible checks and limits

Historical T20 execution evidence: [2026-10-02 QA results](../qa/PROMPT_INJECTION_QA.md), including regression and adversarial browser cases on nginx/API/PostgreSQL with a mock model. Those results do not certify T22's detector or current prompt versions.

Run `npm run qa:security:signals` against `incident_assistant_test` using the normal test environment. It includes delimiter/prompt construction checks, 27 signal fixtures (21 attacks, four ordinary inputs, two legitimate quoted attack reports), six deliberately declared evasions, metadata/privacy checks, and nine API/PostgreSQL scenarios with a mock model. These verify software behavior, not model resistance. Full regression uses `npm run test:coverage`, `npm run test:web`, `npm run qa:eval` and browser suites. Paid real-provider evaluation is separate and requires approval; historical live evidence is not a new certification of this change.

Known misses include base64, HTML entities, Cyrillic homoglyphs, long gaps and semantic paraphrases/output manipulation. Rules cover selected English/Spanish forms, not all languages or obfuscations. A match on a quoted attack is expected; it illustrates why automatic blocking is not enabled. A passing test asserting a miss documents the limit, not successful detection. No statistically meaningful sensitivity, false-positive rate or semantic-accuracy claim follows from this curated set. Logging an exfiltration signal does not prevent exfiltration. Separate PII protection replaces detected entities before forwarding, but may miss data; explicit disabled mode forwards unprotected content. General offline regressions disable PII and do not certify the real detector.

The historical authorized [live evaluation](../qa/PROMPT_SECURITY_LIVE.md), 2026-10-02, **FAILED**: rubric pressure changed summary/classification and produced a fabricated restoration. The observer emitted no signal and that revision's checks did not reject it. A legitimate report exposed punctuation-sensitive URL rejection. Findings remain in their original report, not a measurement of current v7/v9. No reviewer model was added.

## Future options, not implemented

The subsequent [paid GPT comparison](../qa/PROMPT_SECURITY_GPT.md) also exposed instruction-following in the raw rubric answer and accepted attachment-authorization claims. Rejection of one malicious response depended on missing quotes/uncertainty, not semantic detection; a clearly labeled offline variant with one valid quote passed. Model selection alone has not resolved the measured problem. Shared budget exhausted at 15; no guard was evaluated.

A dedicated local classifier can broaden detection without a generative LLM, but introduces weights/runtime, latency and threshold calibration. An independent LLM reviewer could classify the input or compare an answer with authorized evidence; it adds cost, latency, data exposure and its own susceptibility to injection and judgment errors. An agent can orchestrate those steps but is not itself a guarantee or a necessary dependency. Any future enforcement needs measured false positives/negatives, adversarial model tests, timeout/fail-open or fail-closed policy, and server-side authorization for every tool. A second opinion remains evidence for review, not proof of truth. This assessment currently prioritizes the smaller observable layer and preserves the no-tools boundary.
